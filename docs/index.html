Super Mario Bros. Arbitrary Code Execution: A Direct Single-Step RAM Jump in MesenCE

How we discovered a novel 6502 JumpEngine off-by-one primitive in SMB1 that bypasses cartridge swapping, open-bus state corruption, and multi-stage stack manipulation.

Arbitrary Code Execution (ACE) inside classic console ROMs remains one of the most technical domains in reverse engineering. While prior Super Mario Bros. (SMB1) exploit chains relied on multi-stage level loader redirections, open-bus CPU fetches, stack RTI manipulation, and pre-populated RAM state from cartridge swapping, our research uncovered a direct, single-step Arbitrary Code Execution vector in the SMB1 enemy dispatch engine.

By resolving a subtle discrepancy between disassembler labels and the effective arithmetic base address used by the 6502 JumpEngine, we identified that spawning Enemy ID $85 (natively obtainable via World $4B Bowser fireball kills) forces the CPU dispatch pointer directly into NES internal RAM ($03D0).

Disambiguating JumpEngine: The $C891 Discovery

In SMB1, enemy behavior dispatches are handled by RunEnemyObjectsCore at $C882:

SMB1 Assembly — Enemy Object Dispatcher ($C882) 
LDX ObjectOffset
LDA #$00
LDY Enemy_ID,x
CPY #$15
BCC JmpEO          ; IDs < $15 use index 0 -> RunNormalEnemies
TYA
SBC #$14           ; IDs >= $15 use index = Enemy_ID - $14
JmpEO:
JSR $8E04          ; JumpEngine

The core vulnerability relies on how JumpEngine at $8E04 parses return addresses from the MOS 6502 stack:

SMB1 Assembly — JumpEngine ($8E04) 
ASL          ; A = index * 2
TAY
PLA / STA $04
PLA / STA $05
INY / LDA ($04),y -> $06
INY / LDA ($04),y -> $07
JMP ($0006)

On the 6502 CPU, JSR pushes JSR_address + 2 to the call stack—specifically pointing to the address of the high operand byte. Standard ROM disassemblers label the jump table starting at $C892. However, because JumpEngine pulls the pushed return address directly, its effective base address is $C891 (one byte earlier).

$$\text{target} = \text{ROM16}\left[ \text{\$C891} + 2 \times \text{index} + 1 \right] \pmod{256}$$

World 75 Bowser Fireball Trigger

In an unpatched ROM playthrough, Enemy ID $85 is generated naturally through the HurtBowser routine ($D76D):

SMB1 Assembly — HurtBowser ($D76D) 
LDY WorldNumber
LDA $D736,y        ; Read from BowserIdentities table
STA Enemy_ID,x

The BowserIdentities array is 8 bytes long (located at $D736). When WorldNumber ≥ 8, the index reads out-of-bounds into adjacent ROM code bytes. For World 75 ($4B):

$$\text{\$D736} + \text{\$4B} = \text{\$D781} \longrightarrow \text{ROM Value } \text{\$85}$$

Defeating Bowser with fireballs in World 75 assigns Enemy ID $85 to the active slot, causing the subsequent per-frame dispatch to immediately execute 6502 machine code located at NES RAM $03D0.

Host-Side Security Findings in MesenCE

During harness validation under AddressSanitizer (ASAN), two host-side vulnerability vectors were also identified within MesenCE core loaders:

  • NSFE Loader Stack Buffer Overflow: Core/NES/Loaders/NsfeLoader.h parses time/fade chunks with an unbounded index loop targeting NsfHeader::TrackLength[256], enabling a crafted NSFE file to overwrite adjacent stack memory in NesConsole::LoadRom. (PoC: fuzz/poc_time_overwrite.nsfe).
  • VS System Mapper Array OOB Read: Core/NES/Mappers/VsSystem.h:68 performs a C-style cast that mis-sizes array bounds during mapper 99 reads.
